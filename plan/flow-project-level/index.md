## Decisions

- D1 — Three sub-plans in order — the mechanical rename, then the shared rules, then the project manager and its stage skills — each with its own milestone and commit; renaming first means every later plan cites the final names (E5).
- D2 — 01-rename is one commit holding every rename, the gate lists and the version, because *One fact, one value* and the gates require the names to change together; it moves no text between files, so its review is by search (E3, E5).
- D3 — Tier normal for all three: no full-tier trigger — no schema, stored or wire format (the gate parses no component name, E4), no secret, no money, and no code that decides who may do what in a product. D9's removal of `Skill` from the planner's `tools:` only narrows what one agent of this plugin may call, a list the harness enforces; `glab:product-planner` already preloads its skill without the `Skill` tool, the precedent (manager's decision, plan check round 1). The user approves the master because the work split.
- D4 — `glab:session-rules` to at most 13312 bytes is the manager's decision under Rule 3, relayed in the dispatch; the override text is compressed in place rather than moved to a reference file, so naming a model costs no extra read (the audit's 11 KB option is not taken).
- D5 — `glab:project-manager` keeps the titles *The pipeline*, *Pick the tier* and *Your skills — this level only*, so the hook text and its two tests change only in 01-rename (E7).
- D6 — The new stage skills are `glab:project-plan-accept` (Stage 1, the manager's side), `glab:project-plan-analyze` (Stage 1b) and `glab:project-record` (Stage 8), the audit's names under the user's `glab:project-*` scheme; `glab:project-analyze` keeps Stages 3 and 6b only (F12).
- D7 — F4: the planner writes the tier line by the criteria, which move to `glab:project-plan` Step 0; the manager accepts it or sends the plan back to be raised, in `glab:project-plan-accept`, and a raise after acceptance is the manager's `## Decisions` overrule line.
- D8 — F5: the Stage 3 and Stage 6b dispatches carry the slug only, and the `result.md` summary is for the user, because the analyzer never reads it (E7); written once, in `glab:project-analyze`.
- D9 — F3: `glab:project-planner` loses `:20`'s Skill-tool sentence and the `Skill` tool, whose only use that sentence is (E7); nothing the planner acts on stays in the manager.
- D10 — F10: a new shared skill `glab:severity` holds the four levels and their meanings, preloaded instead of `glab:audit` by the four agents that use only that table (E7 adds `product-analyzer` to F10's three); `glab:audit` points at it, and the *One fact* entry for the levels moves with it.
- D11 — F11: each pre-0.11.0 compatibility clause stays only in the role file that acts on it, and its copies in the manager and the stage skills go; dropping the clauses for good is a follow-up, not this change.
- D12 — F22: `glab:bootstrap` to at most 6144 bytes; the steps that restate the hook or the manager become pointers, and the four tool hazards stay reachable from the payload, none dropped (*Comments and recorded incidents are kept*).
- D13 — F27 is left as it is: the Go test policy in the developer is the user's; it goes to the record as a follow-up.
- D14 — F21: the pipeline says to invoke a stage skill once per context, and again only after a compaction; whether a second call re-injects the body is UNVERIFIED and goes to the record.
- D15 — No sub-plan edits `docs/specs/`; text that leaves the payload for a spec is named in its sub-plan's plan and carried by the record (`master.md` *Record*).
- D16 — The skill count goes 21 (01) → 22 (02, `severity`) → 25 (03); each commit's `AGENTS.md` *Gates*, `README.md` counts and skills gate match its own tree.

It adds one line for plan folders begun before 0.15.0: their `- model: glab:<old agent> …` lines (`session-rules:121`) name agents that no longer exist, and are rewritten to the new name before the folder's next dispatch.
