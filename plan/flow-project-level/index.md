## Decisions

- D1 — Three sub-plans in order — the mechanical rename, then the shared rules, then the project manager and its stage skills — each with its own milestone and commit; renaming first means every later plan cites the final names (E5).
- D2 — 01-rename is one commit holding every rename, the gate lists and the version, because *One fact, one value* and the gates require the names to change together; it moves no text between files, so its review is by search (E3, E5).
- D3 — Tier normal for all three: no full-tier trigger — no schema, stored or wire format (the gate parses no component name, E4), no secret, no money, and no code that decides who may do what in a product. D9's removal of `Skill` from the planner's `tools:` only narrows what one agent of this plugin may call, a list the harness enforces; `glab:product-planner` already preloads its skill without the `Skill` tool, the precedent (manager's decision, plan check round 1). The user approves the master because the work split.
- D4 — `glab:session-rules` to at most 13312 bytes is the manager's decision under Rule 3, relayed in the dispatch; the override text is compressed in place rather than moved to a reference file, so naming a model costs no extra read (the audit's 11 KB option is not taken).
- D5 — `glab:project-manager` keeps the titles *The pipeline*, *Pick the tier* and *Your skills — this level only*, so the hook text and its two tests change only in 01-rename (E7).
- D6 — The new stage skills are `glab:project-plan-accept` (Stage 1, the manager's side), `glab:project-plan-analyze` (Stage 1b) and `glab:project-record` (Stage 8), the audit's names under the user's `glab:project-*` scheme; `glab:project-analyze` keeps Stages 3 and 6b only (F12).
- D7 — F4: the planner writes the tier line by the criteria, which move to `glab:project-plan` Step 0; the manager accepts it or sends the plan back to be raised, in `glab:project-plan-accept`, and a raise after acceptance is the manager's `## Decisions` overrule line.
- D8 — F5: the Stage 3 and Stage 6b dispatches carry the slug only, and the `result.md` summary is for the user, because the analyzer never reads it (E7); written once, in `glab:project-analyze`.
- D9 — F3: `glab:project-planner` loses `:20`'s Skill-tool sentence and the `Skill` tool, whose only use that sentence is (E7); nothing the planner acts on stays in the manager.
- D10 — F10: a new shared skill `glab:severity` holds the four levels and their meanings, preloaded instead of `glab:audit` by the four agents that use only that table (E7 adds `product-analyzer` to F10's three); `glab:audit` points at it, and the *One fact* entry for the levels moves with it.
- D11 — F11: each pre-0.11.0 compatibility clause stays only in the role file that acts on it, and its copies in the manager and the stage skills go; dropping the clauses for good is a follow-up, not this change.
- D12 — F22: `glab:bootstrap` to at most 6144 bytes; the steps that restate the hook or the manager become pointers, and the four tool hazards stay reachable from the payload, none dropped (*Comments and recorded incidents are kept*).
- D13 — F27 is left as it is: the Go test policy in the developer is the user's; it goes to the record as a follow-up.
- D14 — F21: the pipeline says to invoke a stage skill once per context, and again only after a compaction; whether a second call re-injects the body is UNVERIFIED and goes to the record.

- D20 — `glab:security` Part 2 and the `push` rationale stay as they are and go to the record as levers: neither is in the user's words, and G5's caps hold without them.
- D21 — G6's session id: `manager-bootstrap.sh` reads `session_id` from its hook input with `jq`, as `context-size.sh:90` already reads `transcript_path` (E10), and uses it only when it matches `^[A-Za-z0-9][A-Za-z0-9_-]{0,127}$`, so no id can name a path outside `plan/handoff/`; both levels' text then gains one line naming `plan/handoff/<id>.md`. No input, input that is not JSON, no `session_id`, an id that fails the match, or no `jq` gives instead one line with the fixed words `no session id`, telling the manager to name its file `plan/handoff/<UTC yyyymmddThhmmss>Z.md` and say so once; the contract is unchanged — exit 0, one object whose only key is `hookSpecificOutput`, the plain text (then always the no-id line) when `jq` fails. - D22 — The handoff file holds the current state only — the slug, stage, round and next dispatch in flight, the sessions and briefs waited on, and decisions no plan file holds — rewritten in place, never appended to, at most 4096 bytes (`wc -c`); finished work is in the record and git. 4096 makes the user's "small" checkable, and the file this session moved by hand is 2968 bytes (E10).
- D23 — "Completed" is readable from the file alone: it opens with `- status: in-flight` or `- status: completed`, `- session: <id>` and `- updated: <UTC ISO 8601>`; the manager writes `completed` when its last task reaches the task boundary, just before it removes the file, so a session that ends between the two leaves a file any reader may remove.
- D24 — At the task boundary of `session-rules` Rule 2 (after the Stage 8 record's push, or Stage 7 with no plan folder — the existing `/clear` point) the manager writes `- status: completed` and removes its own file under D30's standing approval, in the fixed words "remove your own handoff file"; the next task opens a new one. No other step of this session removes its own file; D25 governs other sessions' files.
- D25 — Liveness: a reader cannot tell a live session from a dead one — the hook input carries no process id, and reading another session's transcript for its age is ruled out (`session-rules` Rule 2: never read the transcript) — so `bootstrap` step 5 removes other sessions' `completed` files without asking (the user's "just remove them"), lists each other `in-flight` file (session, slug, stage, updated) and takes one over — its state into this session's file, the old file removed — only on the user's yes, because an untracked file is not recoverable (`glab:security` *Destructive operations are proven*) and D30's approval does not cover it. After a compaction the session keeps writing the file its own summary names as its own, even when the hook names another id, and says so once; nothing is moved or removed, so an id that changes (E9) needs no ask.
- D26 — `plan/SESSION-HANDOFF.md` is a legacy file: `bootstrap` step 5 reads it as one more `in-flight` file of an unknown session (D25) and removes it only on the user's yes; no other payload, `AGENTS.md` or test line names it (E10's other namings change or go). Repos on glab 0.14 or earlier still have one.
- D27 — This repo gets a root `.gitignore` holding `plan/handoff/`, listed in `AGENTS.md` *Layout*; it has none today (E10). The payload says `plan/handoff/` is never committed, and no `glab` step edits a user repo's `.gitignore`, which is its owner's file.

- D29 — G6 goes to 02-shared-rules, which already rewrites `session-rules` and `bootstrap`; the version stays 0.15.0, raised once in 01 (D19), because 02 ships in the same push.
- D30 — The removal rule lives in the payload, with its owner: `glab:session-rules` Rule 2, which owns the handoff file, states the one standing approval — the user's instruction of words 5 covers removing a file `plan/handoff/<id>.md` whose first line is `- status: completed`, and nothing else — in those words, so no subdirectory, no other file name and no in-flight file that quotes the line in its body is covered — and the two rules it excepts, `glab:security:146` (untracked files: stop and ask) and `glab:session-rules:99` (confirmation before every destructive action), each gain a pointer of a few words, "except the standing approval of `glab:session-rules` Rule 2"; their bytes count against G5's caps, `security`'s in both session starts. An exception only in `AGENTS.md` would not reach an installed manager, which reads the payload (plan check round 1, finding 1).
